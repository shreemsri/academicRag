================================================================================
SCHOLARRAG: DEEP-DIVE TECHNICAL DOCUMENTATION
================================================================================

1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
ScholarRAG is a highly advanced, local-first hybrid Retrieval-Augmented Generation (RAG) platform. Unlike generic LLM chat interfaces, ScholarRAG focuses heavily on academic and professional document integrity, solving the LLM hallucination problem by grounding all answers strictly within user-uploaded contexts and forcing verifiable, chunk-level citations.

The core philosophy revolves around decoupling heavy, GPU-bound tasks (embedding and reranking) from the actual generative tasks, allowing the application to run smoothly on consumer hardware while delegating generation to ultra-fast models like Google's Gemini 3.5 Flash.

2. SYSTEM ARCHITECTURE 
--------------------------------------------------------------------------------
ScholarRAG operates on a decoupled client-server architecture:

2.1. Frontend (React 18 + Vite + TypeScript)
- The frontend operates as a Single Page Application (SPA).
- State Management: Uses Zustand for persisting the selected workspace and chat history UI states.
- SSE Consumer: Instead of standard REST polling, the chat interface consumes Server-Sent Events (SSE). This allows the UI to render citations, metadata, and token streams instantly, exactly as they are generated by the backend LLM.
- Styling: Implements TailwindCSS for utility-first styling and Radix UI for accessible primitives, using a "glassmorphism" design system (semi-transparent overlays, blurs).

2.2. Backend (FastAPI + Python 3.12)
- Server: Uvicorn ASGI server handles asynchronous requests.
- Async I/O: Heavy ML tasks (like running PyTorch models) are offloaded to `asyncio.to_thread()` to prevent blocking the main event loop, allowing high concurrency.

3. DATA MODELS & STORAGE
--------------------------------------------------------------------------------
The application utilizes a two-tier database strategy: Relational (SQLite) and Vector (ChromaDB).

3.1. Relational Database (SQLite via SQLModel)
- Workspace Table: Stores `id`, `name`, `created_at`.
- Document Table: Stores metadata about uploaded files (`id`, `workspace_id`, `filename`, `file_size`, `status`).
- ChatMessage Table: Stores historical chat interactions (`id`, `workspace_id`, `role`, `content`, `citations`).

3.2. Vector Database (ChromaDB)
- Hosted locally.
- Collection Strategy: Each workspace has its own distinct ChromaDB collection (named via the `workspace_id` UUID). This ensures multi-tenant isolation, meaning a query in Workspace A cannot accidentally retrieve chunks from Workspace B.

4. CORE WORKFLOWS (DEEP DIVE)
--------------------------------------------------------------------------------
4.1. The Ingestion Pipeline (File -> Vectors)
When an academic paper (PDF) is uploaded:
1. Format Unification: If the file is a PPTX or DOCX, it is first mapped to a PDF format if required, though `PyMuPDF` handles native PDF layout natively.
2. Text Extraction: `PyMuPDF` runs over the document. It doesn't just strip raw text; it utilizes spatial heuristics (font size, bolding, block position) to determine where paragraphs end and where headers begin.
3. Recursive Chunking: The text is passed into LangChain's `RecursiveCharacterTextSplitter`. Chunk size is set to ~1000 tokens with a 200-token overlap. This overlap ensures that a sentence split across two chunks doesn't lose semantic meaning.
4. Embedding: Each chunk is passed through the locally loaded `BAAI/bge-small-en-v1.5` model. This model converts the string of text into a 384-dimensional dense floating-point vector.
5. Sparse Indexing: Concurrently, the raw text of the chunk is tokenized and added to a BM25 In-Memory index (Sparse retrieval).
6. Commit: Vectors and metadata are committed to ChromaDB.

4.2. The Generation Pipeline (Query -> Streaming Answer)
1. Query Vectorization: The user's query ("What is Machine Learning?") is embedded using `bge-small-en-v1.5`.
2. Dense Retrieval (ChromaDB): Fetches the top 20 chunks mathematically closest to the query vector using Cosine Similarity.
3. Sparse Retrieval (BM25): Fetches the top 20 chunks based on exact keyword overlap.
4. Reciprocal Rank Fusion (RRF): The system combines the ranks from both searches. A chunk that scores high in BOTH dense (semantic meaning) and sparse (exact keywords) searches receives an exponentially higher RRF score.
5. Cross-Encoder Reranking: The top 10 fused chunks are fed into `BAAI/bge-reranker-base`. A cross-encoder evaluates the user's query and the chunk text *simultaneously*, outputting a highly accurate relevance score (0.0 to 1.0).
6. Context Assembly: The top 3-5 chunks post-reranking are injected into a rigid system prompt template.
7. Generative LLM: The prompt is sent to `gemini-3.5-flash`. The LLM is strictly instructed to only use the provided context and to append `[doc_id]` citations.
8. SSE Stream: The backend intercepts the LLM token stream and yields it chunk-by-chunk to the HTTP response object, which the frontend visualizes.

5. AI MODEL SPECIFICATIONS
--------------------------------------------------------------------------------
- Dense Embedding: `BAAI/bge-small-en-v1.5`
  - Dimensions: 384
  - Max Context: 512 tokens
  - Footprint: < 200MB RAM. Exceptional at english-language academic texts.

- Cross-Encoder Reranker: `BAAI/bge-reranker-base`
  - Footprint: ~1.1GB RAM. 
  - Why a reranker? Standard embedding models compare texts independently (Bi-Encoders). A Cross-Encoder processes the query and text through attention layers together, yielding massively improved accuracy at the cost of higher latency. This is why it is only run on the top 10 results.

- Generator: `gemini-3.5-flash`
  - Access: via Google Generative AI REST API (`generativelanguage.googleapis.com`).
  - Speed: Capable of immense token generation speeds (Time-to-first-token < 1s).

6. SCALABILITY & FUTURE OPTIMIZATIONS
--------------------------------------------------------------------------------
While ScholarRAG is designed to run locally, it is architected for enterprise scale:
- Database Swap: The `get_db()` dependency injection allows replacing SQLite with PostgreSQL instantly via SQLAlchemy config changes.
- Vector DB Swap: ChromaDB can be swapped for a cloud-hosted Pinecone or Milvus cluster without changing the retrieval logic.
- Model Inference: The embedding and reranking models are currently run on CPU via PyTorch. They can be accelerated by installing `onnxruntime-gpu` (NVIDIA) or `onnxruntime-silicon` (Apple M-Series) for a 10x-50x speedup in document ingestion times.
